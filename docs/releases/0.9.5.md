# OpenRad 0.9.5 — Automatic Windows Radmin VPN conflict recovery

Windows users migrating from official Radmin VPN can connect without manually
stopping its service and disabling its adapter. When an enabled **Famatech Radmin
VPN Ethernet Adapter** holds a `26.x.x.x` address, both OpenRad's desktop and CLI
use their administrator permission to register a temporary SYSTEM task. The
embedded worker stops the service running `RvControlSvc.exe`, force-terminates
remaining processes with that executable name, and disables the selected official
adapter. OpenRad removes the task, rechecks active interfaces, and continues the
same connection attempt. The application keeps the user's profile/credentials.

Recovery uses built-in Windows PowerShell and Task Scheduler, works offline, and
does not download PsExec. The worker's execution limit is thirty seconds, task
completion is awaited for up to forty seconds, and interface readiness is retried
for up to ten seconds. Adapter descriptions and identities are checked again in
the worker. Unrelated VPN conflicts and stale OpenRad addresses remain errors.

The official adapter remains disabled and its service stopped after disconnect.
OpenRad does not uninstall Radmin or change its service startup setting. To switch
back, close/disconnect OpenRad, enable the official adapter in Windows network
settings, and start Radmin's service or restart Windows. See [Windows setup and
recovery](../windows.md#switching-from-official-radmin-vpn).

## Packages

- Newly compiled Windows x64 CLI, desktop and setup worker, the offline setup EXE,
  and a ZIP with guides/build metadata/checksums. The signed TAP-Windows6 9.27.0
  driver and its corresponding source/licenses are carried forward unchanged.
- The **exact `openrad-v0.9.0-linux-x86_64.tar.gz` archive from release 0.9.0** is
  reused, with SHA-256 `d5893fd5f0df173fc74af70b6b8cbf3d1587f3278b54ba59f13a67bf031ca055`.
  Linux runtime behavior has no changes in this release. Its binaries, internal
  documentation and build metadata retain version **0.9.0**. The filename keeps
  that version so the provenance of the reused build is clear.

## Verification and Windows status

- **191 default workspace tests passed on Linux**, including nine new recovery
  policy/retry regressions; three optional tests remained ignored.
- Rust formatting and workspace/all-targets Clippy with warnings denied passed
  for Linux and the Windows GNU target. Windows workspace release binaries and
  all Windows test executables cross-compiled successfully with Rust 1.98.1 and
  MinGW-w64. The Windows tests were compiled, not executed.
- **19 synthetic PowerShell recovery cases passed**, covering service/process
  stop order, exact adapter selection, replacement/process-exit races, denied
  operations, SYSTEM task configuration, completion and cleanup. Eleven existing
  adapter setup regressions and script syntax checks also passed.
- Eight synthetic NSIS installer-flow cases passed under an isolated Wine prefix.
  These use dummy executables and do not exercise the real VPN or Windows driver.
- Packaging verifies PE/DLL imports, the installer administrator manifest,
  extracted installer payload hashes, pinned signed driver/source hashes and
  ZIP/checksum integrity. The reused Linux archive matches its published 0.9.0
  SHA-256 byte for byte.

Windows support remains experimental. Previous Windows 10 success was reported
by a user for 0.9.0; the release builder runs Linux and has not executed the new
SYSTEM recovery on Windows. A real migration test with official Radmin's service
and adapter installed is still needed, including service permissions, task
scheduling, adapter disabling and the resulting connection. Report results via
[GitHub issues](https://github.com/gringoestrangeiro/openrad/issues/new), keeping
credentials and packet captures private.
