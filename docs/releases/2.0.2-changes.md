# OpenRad 2.0.2 — Maintenance change inventory

This document covers [pull request #9](https://github.com/gringoestrangeiro/openrad/pull/9)
and the direct-path follow-up merged with it. It records the source changes included in the 2.0.2 maintenance release. Release artifacts and validation details are documented in [2.0.2.md](2.0.2.md).
The 2.0.2 maintenance update does not intentionally change the OpenRad wire protocol.

## Main changes

- **Direct paths:** While a direct attempt has already heard from the peer (a valid UDP punch or matching TCP rendezvous), relay authentication waits up to 16 seconds after its ticket instead of preempting it. UDP rendezvous runs for 14 seconds in both roles. A punch from another port on an authenticated candidate's IP address is admitted (at most eight learned ports), covering endpoint-dependent NATs without scanning. UES mapping requests are resent, a lone reply is used at the deadline, and disagreement still advertises the first observation. An established UDP channel is not closed for a missing acknowledgement while the peer is still sending.
- **Incoming offers:** The accepting side requests its own relay ticket (op 22) after a 2-second direct preference (300 ms when relay-only), so incoming setups can fall back to relay. A service refusal or disconnect within five seconds disables further requests for the process. Offers that receive nothing for 15 seconds are abandoned early. The Android engine carries the same changes.
- **Connection reliability:** Allocate the remaining TCP connect deadline across unresolved IP addresses so a slow IPv6 candidate does not consume the entire timeout before IPv4 is tried.
- **Windows daemon:** Start the CLI-managed background process without inheriting redirected CLI stdout/stderr handles; report process exits and platform-specific startup diagnostics.
- **Desktop persistence:** Atomically replace settings and network-preference JSON files using unique temporary names; synchronize the containing directory after a rename on POSIX.
- **Windows uninstall:** Add a Settings confirmation flow. Start the installed NSIS uninstaller through `ShellExecuteExW` with the `runas` verb and `/FROMSETTINGS` argument. The NSIS uninstall flow is designed to preserve identity, profiles, preferences, and logs.
- **Radmin recovery:** Retain pending asynchronous diagnostic reads when a named-pipe connection precedes the diagnostic write; include a local delayed-write regression test.
- **Localization:** Add uninstall strings and preserve Portuguese, Russian, and Vietnamese Unicode text.
- **Test stability:** Accept either a cancellation error or a notification-only `Ok(false)` when the UDP stop flag and wake notification race.

## Verification and limitations

The merged 2.0.2 branch passes the Linux workspace tests, Rust formatting, Linux and
Windows-target Clippy, and `scripts/check-sync.py`. Android unit tests were reported by
the contributor. GitHub CI runs on the pull request and the follow-up commit.

The Windows end-to-end VPN connection between two physical peers, a native installation/uninstallation cycle, and the full elevated Radmin recovery have **not** been established by these tests. Live service behavior for the new direct-path and relay-request timing has not been measured against real NATs.
The installer packaging pipeline requires pinned driver inputs, cross-built Windows binaries, NSIS and other tooling; presence of this document only removes its previously missing release-note input, not those other prerequisites.

Windows support remains experimental. Do not disable Windows security protections or interrupt active VPN services to test these paths.
